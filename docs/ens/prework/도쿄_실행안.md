# OneIntent Pay — ETHGlobal Tokyo 2026 실행안

> **Pay `merchant.eth` from whatever chain your money is on.**  
> 사용자는 상점의 체인과 결제 토큰을 고르지 않는다. ENS 결제 프로필과 Uniswap의 cross-chain routing을 이용해 원하는 상점에 원하는 금액만 지불한다.

## 1. 결정

### 추천: Vault보다 Payment

3인 팀의 ETHGlobal Tokyo 36시간 프로젝트로는 **Payment를 1순위**로 추천한다.

| 기준 | Vault | Payment |
|---|---:|---:|
| 10초 안에 이해되는가 | 7 | 10 |
| chain abstraction이 눈에 보이는가 | 7 | 10 |
| 실제 cross-chain destination call 난이도 | 높음 | 낮음 |
| Uniswap `recipient` 기능과의 적합성 | 보통 | 매우 높음 |
| ENS가 핵심 기능이 되는가 | 약함 | 매우 높음 |
| 3인·36시간 완주 가능성 | 6 | 9 |

Vault는 자산이 목적 체인에 도착한 뒤 `deposit()` 호출과 share 수령까지 처리해야 하므로 cross-chain composition이 하나 더 필요하다. Payment는 swap/bridge의 output recipient를 상점 주소로 지정하는 순간 최종 행동이 된다.

Vault를 버리는 것은 아니다. Payment happy path가 완성된 뒤 **상점 매출을 vault로 sweep하는 treasury 기능**으로만 확장한다. 처음부터 둘을 동시에 만들지는 않는다.

## 2. 행사와 스폰서 전제

- 행사: ETHGlobal Tokyo 2026
- 일정: 2026년 9월 25~27일
- 팀: 3명
- 2026년 8월 29일 현재 공식 prize 상세 페이지는 아직 확인되지 않는다.
- 공개 행사 안내에 노출된 파트너 후보: World, ENS, Uniswap Foundation, Sui, 1inch

따라서 지금은 bounty의 세부 문구를 추측해 기능을 억지로 붙이지 않는다. 코어 제품은 **Uniswap + ENS** 두 가지를 깊게 사용하고, 세 번째 sponsor는 현장에서 prize 조건이 공개된 뒤 고른다.

### 예상 제출 우선순위

1. **Uniswap Foundation** — quote, swap/bridge, Chained Actions, custom recipient가 제품의 실행 엔진
2. **ENS** — merchant identity, multichain settlement address, 결제 설정을 제공하는 discovery layer
3. **현장에서 결정**
   - World가 payment/Mini App을 원하고 경로가 안정적이면 World
   - 1inch가 Fusion+ 또는 cross-chain intent를 강하게 요구하고 Uniswap 경로가 막히면 1inch adapter
   - Sui가 단순 부가 연동만 요구한다면 범위 보호를 위해 과감히 제외

스폰서 SDK는 많이 넣는 것보다 **없으면 제품이 동작하지 않을 정도로 깊게 쓰는 것**이 중요하다.

## 3. 최종 제품 정의

### 한 문장

OneIntent Pay는 ENS 이름을 멀티체인 결제 계정으로 만들고, payer의 여러 체인 자산 중 가장 적절한 자산을 찾아 상점이 원하는 token과 chain으로 결제하는 payment agent다.

### 예시

> “`tokyo-cafe.eth`에 5 USDC 결제해줘. Base의 자산을 우선 사용하고 총비용은 5.10 USDC를 넘기지 마.”

OneIntent가 다음을 처리한다.

1. `tokyo-cafe.eth`의 settlement profile 조회
2. payer가 가진 지원 체인의 token balance 조회
3. 가능한 same-chain/cross-chain Uniswap quote 비교
4. recipient, 최대 지출, 최소 수령, deadline 검증
5. 사용자가 승인할 실행 계획 생성
6. payment escrow 도착과 merchant 정산 event 확인

## 4. 왜 새로운가

기존 crypto checkout은 대개 다음 중 하나를 사용자에게 요구한다.

- 특정 체인으로 미리 bridge
- 특정 stablecoin을 미리 보유
- 결제 화면에서 source chain과 token을 직접 선택
- 상점의 raw address를 확인

OneIntent Pay에서는 merchant가 “어디서 돈을 받을 수 있는가”를 ENS profile에 공개하고, agent가 payer의 자산과 route를 맞춘다.

> Chain abstraction is not always “bridge everything.” Sometimes the best route is discovering a settlement chain both sides already share.

Agent는 먼저 same-chain exact-output 경로를 찾고, 필요할 때만 cross-chain 경로를 사용한다. 불필요한 bridge를 피하는 것도 chain abstraction의 일부다.

## 5. 데모 사용자 흐름

### Merchant 화면

1. `tokyo-cafe.eth`로 로그인한다.
2. ENS에서 다음 payment profile을 읽는다.
   - Base settlement address
   - Unichain settlement address
   - accepted token: USDC
3. 5 USDC invoice를 생성한다.
4. QR/link가 만들어진다.

### Payer 화면

1. QR을 스캔하거나 자연어 명령을 입력한다.
2. agent가 Base, Arbitrum, Unichain 등 **실제로 지원하기로 고른 2개 체인만** 조회한다.
3. 다음과 같은 결과 중심 preview를 보여준다.

```text
Paying       tokyo-cafe.eth
Merchant gets  5.00 USDC on Unichain
You spend       up to 5.08 USDC on Base
Estimated time  45–90 sec
Route           Hidden by default · View details
Refund          Available after invoice expiry if underpaid
```

4. 사용자가 실행 계획을 승인한다.
5. UI가 `Payment authorized → Routed → Escrow funded → Merchant settled`를 보여준다.
6. 두 번째 화면의 merchant dashboard가 실시간으로 `PAID`로 바뀐다.
7. invoice ID, payer, merchant ENS, amount, transaction hash를 보여준다.

## 6. ENS를 장식이 아닌 핵심으로 쓰는 방법

### Multichain address records

ENS의 chain별 address record에서 merchant 수령 주소를 해석한다. EVM chain ID에서 ENSIP-11 coin type을 계산한다.

```ts
const baseCoinType = toCoinType(8453)
const unichainCoinType = toCoinType(130)
```

merchant가 체인마다 다른 smart account/treasury 주소를 사용할 수 있으므로 단순히 같은 EOA 주소를 하드코딩하지 않는다.

### Custom text record

```text
com.oneintent.payment = {
  "version": 1,
  "accepted": [
    { "chainId": 8453, "token": "USDC" },
    { "chainId": 130,  "token": "USDC" }
  ],
  "maxSlippageBps": 50
}
```

실제 값은 compact JSON 또는 IPFS/HTTPS manifest URI로 저장할 수 있다. 해커톤 MVP에서는 JSON text record를 읽되 schema validation을 반드시 한다.

### ENS가 실패하면

- name이 resolve되지 않으면 결제를 중단한다.
- chain address record가 없으면 그 chain을 후보에서 제외한다.
- payment record가 잘못됐으면 fallback을 추측하지 않고 에러를 표시한다.
- resolved raw address와 ENS name을 승인 preview에 함께 보여준다.

이렇게 해야 “ENS avatar만 보여준 integration”이라는 평가를 피할 수 있다.

## 7. Uniswap을 핵심 실행 엔진으로 쓰는 방법

### Quote

후보 source balance와 merchant settlement option의 조합마다 `/quote`를 요청한다.

```json
{
  "tokenIn": "0xSourceToken",
  "tokenOut": "0xUSDC",
  "tokenInChainId": 8453,
  "tokenOutChainId": 130,
  "amount": "5080000",
  "type": "EXACT_INPUT",
  "swapper": "0xPayer",
  "recipient": "0xInvoiceEscrow",
  "slippageTolerance": 0.5
}
```

- same-chain 결제는 가능하면 `EXACT_OUTPUT`으로 5 USDC를 정확히 맞춘다.
- cross-chain Chained Actions는 exact-input 기반이므로 예상 output이 invoice amount보다 안전 margin만큼 큰 route만 선택한다.
- custom `recipient`에는 merchant 주소 대신 invoice별 escrow 주소를 넣는다.
- quote에 포함된 gas, time, minimum output을 policy validator가 재검사한다.

### Execute

- `CLASSIC`, `BRIDGE`이면 `/swap`
- `DUTCH_*`, `PRIORITY`이면 `/order`
- `CHAINED`이면 `/plan` 생성 후 active step을 순서대로 실행
- approval이 필요하면 `/check_approval`, Permit2, EIP-5792 batch를 사용
- plan ID를 저장해 새로고침 후에도 실행을 복원한다.

### 중요한 UX 정직성

- 첫 ERC-20 사용에는 approval transaction/signature가 추가될 수 있다.
- `승인 1회`는 Permit2가 준비됐거나 wallet이 EIP-5792 batching을 지원하는 경로에서만 주장한다.
- Chained plan이 여러 user action을 요구하면 UI에 숨기지 않고 `1 of 2`로 표시한다.
- agent가 wallet prompt를 대신 승인하지 않는다.

## 8. InvoiceEscrow contract

Uniswap output을 merchant에게 바로 보내면 결제 transaction과 invoice ID를 온체인에서 강하게 연결하기 어렵다. 그래서 invoice별 deterministic escrow를 사용한다.

### 생성

`InvoiceFactory`가 minimal proxy/clone을 CREATE2로 배포한다.

```solidity
struct Invoice {
    bytes32 invoiceId;
    address merchant;
    address payer;
    address token;
    uint256 amountDue;
    uint64 deadline;
}
```

escrow 주소는 invoice data와 salt로 미리 계산할 수 있다. preview에는 recipient가 이 주소임을 보여준다.

### 정산

1. Uniswap route output이 escrow에 도착한다.
2. 누구나 `settle()`을 호출할 수 있다.
3. `balance >= amountDue`이면 amount due를 merchant에게 보낸다.
4. 초과분은 payer에게 반환한다.
5. `InvoicePaid(invoiceId, payer, merchant, amountDue)` event를 발생시킨다.

### 실패/환불

- amount가 부족하면 정산하지 않고 추가 입금을 기다린다.
- deadline 후 payer가 `refund()`를 호출해 잔액을 회수한다.
- paid invoice는 재정산할 수 없다.
- reentrancy guard, safe transfer, checks-effects-interactions를 적용한다.

### 필수 테스트

- 정확한 금액 정산
- 초과분 payer 반환
- 부족한 금액 settle revert
- deadline 이후 refund
- merchant/payer/token zero address 방지
- initialize 재호출 방지
- 같은 invoice salt 재배포 방지
- settle/refund replay 방지

## 9. Agent와 policy 경계

### Agent

- 자연어 또는 invoice를 `PaymentIntent`로 변환
- balance와 여러 quote를 비교
- 비용/시간/bridge 사용 여부에 따라 계획 추천
- plan step과 실패 원인을 사용자 언어로 설명

### Policy validator

- ENS resolution 결과와 quote recipient 일치
- merchant가 허용한 chain/token인지 검사
- `maxInput`, `minOutput`, deadline 검사
- API가 반환한 transaction의 chain, `to`, calldata target 검사
- invoice escrow bytecode/factory 검증

### Wallet

- 최종 transaction 또는 typed message에 명시적으로 서명

LLM 출력은 절대로 transaction calldata의 source of truth가 아니다.

## 10. MVP와 fallback

### P0 — 심사 가능한 최소 성공

- 실제 ENS name과 두 chain address record resolution
- 지원 체인 2개 balance scan
- Uniswap API 실제 quote
- custom recipient가 invoice escrow인 실제 swap/payment
- invoice escrow `InvoicePaid` event
- merchant dashboard 실시간 갱신
- 실제 transaction hash 1개 이상
- 자연어 → typed `PaymentIntent`

### Cross-chain spike가 성공하면 P0에 포함

- `tokenInChainId != tokenOutChainId`
- `CHAINED` quote와 `/plan` state machine
- plan 새로고침/복원
- destination escrow 정산

### Cross-chain spike가 실패할 때의 정식 fallback

단순 mock bridge를 붙이지 않는다. ENS가 제공하는 두 settlement chain 중 payer 자산이 있는 chain을 선택하고, same-chain exact-output swap으로 결제한다.

이 fallback도 다음 가치를 실제로 증명한다.

- 사용자가 chain을 선택하지 않음
- merchant address가 chain별로 자동 resolve됨
- 사용자가 어떤 token을 가졌든 merchant는 USDC 수령
- 불필요한 bridge를 피함

### P1

- World Mini App/World ID
- second routing adapter
- merchant 매출의 vault sweep
- recurring agent spending policy
- Japanese/Korean localization

## 14. 심사 질문 답변

### “Uniswap UI와 무엇이 다른가?”

사용자는 token pair나 chain을 선택하지 않는다. merchant의 ENS payment profile과 invoice outcome을 기준으로 여러 funding 후보를 평가하고, output을 invoice escrow로 직접 보낸다.

### “왜 AI가 필요한가?”

AI는 결제 금액을 계산하거나 calldata를 생성하지 않는다. 사용자의 자연어 제약을 typed intent로 바꾸고 여러 funding 경로를 설명한다. quote와 실행 검증은 deterministic하다.

### “왜 ENS인가?”

ENS가 없으면 merchant별 chain address와 settlement preference를 중앙 DB에 저장해야 한다. OneIntent에서는 merchant가 자신의 이름 아래에서 이 설정을 소유하고 다른 결제 client도 해석할 수 있다.

### “Cross-chain exact output이 아닌데 5 USDC를 보장하는가?”

same-chain은 exact-output을 사용한다. cross-chain은 예상 output에 safety margin을 두고 escrow가 `amountDue` 이상일 때만 정산한다. 부족하면 paid로 표시하지 않고 deadline 이후 payer가 환불한다.

### “완전히 한 번의 서명인가?”

모든 wallet과 첫 token approval에서 그렇다고 주장하지 않는다. Permit2/EIP-5792가 준비된 경로는 한 번이고, 그 외에는 필요한 action 수를 정확히 표시한다.

## 15. 최종 pitch

### Short

> OneIntent Pay lets you pay `merchant.eth` from whatever chain your money is on. ENS publishes where and how a merchant accepts payment; Uniswap finds and executes the route; an invoice escrow verifies that the merchant actually received the promised amount.

### 한국어

> OneIntent Pay는 사용자가 보유한 자산의 체인과 상점이 정산받는 체인이 달라도 결제할 수 있게 하는 payment agent입니다. ENS가 상점의 멀티체인 결제 프로필을 제공하고, Uniswap이 swap과 cross-chain route를 실행하며, invoice escrow가 약속된 금액의 실제 수령을 온체인에서 검증합니다.

## 17. 지금 바로 준비할 것

해커톤 시작 전에 실제 제품 코드를 미리 작성하면 행사 규칙과 충돌할 수 있으므로, 허용 범위를 먼저 확인한다. 준비는 다음 수준으로 제한한다.

- 각 팀원의 역할과 개발 환경 통일
- Uniswap/ENS/World 문서 읽기와 API key 신청
- 사용할 ENS name 확보
- mainnet에서 쓸 소액 gas/USDC 예산 결정
- UI wireframe와 contract interface를 문서로 합의
- 행사 당일 첫 3시간 spike에 사용할 chain/token 후보 2세트 준비

prize 상세가 공개되면 이 문서의 2번과 12번만 업데이트하고, 제품의 핵심 흐름은 유지한다.
